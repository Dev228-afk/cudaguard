# CudaGuard Limitations

This document explicitly describes what CudaGuard does not do. Documenting limitations is important for credibility and helps users understand the tool's scope.

## Fundamental Scope Limitations

1. **CudaGuard does not generate PTX, SASS, LLVM IR, or CUDA device code.** It is a static analysis tool, not a compiler backend.

2. **CudaGuard does not replace nvcc or clang++.** It runs *before* or *alongside* the real compiler as a diagnostic helper.

3. **CudaGuard does not verify runtime correctness.** Race conditions, memory access violations, and numerical errors are outside its scope.

4. **CudaGuard does not perform performance analysis.** Occupancy, memory coalescing, and warp divergence require profiling tools like Nsight Compute.

## Analysis Limitations

### Template Code

Template-heavy CUDA code may produce incomplete diagnostics:
- Dependent types and names cannot be fully resolved until instantiation.
- CG003 skips calls in dependent contexts to avoid false positives.
- Deeply nested template metaprogramming may not trigger matchers.

### Macro-Expanded Code

Kernel launches generated by macros may have limited source-location quality:
- Diagnostics may point to the macro expansion site rather than the definition.
- Complex macro patterns may prevent AST matchers from recognizing patterns.

### Interprocedural Analysis

Analysis is intentionally limited to single-function scope:
- CG001 only checks sibling statements within the same compound statement.
- CG005 only tracks pointer provenance within a single function.
- Wrapper functions that call `cudaGetLastError()` internally are not recognized.

### Cross-Translation-Unit Analysis

- CG004 can only correlate kernel definitions and launches within the same `.cu` file.
- Kernels defined in headers and launched in a different file may not be fully analyzed.

## Rule-Specific Limitations

### CG001 (Missing Error Check)
- 5-statement lookahead window is arbitrary.
- Custom error-checking macros/functions are not recognized.
- Error checks in called functions are not detected.

### CG002 (Launch Configuration)
- Only literal integer values trigger warnings.
- `dim3` constructors with variable arguments are not analyzed.
- Does not validate that grid size matches problem size.

### CG003 (Host/Device Mismatch)
- Overloaded functions where one overload has `__device__` may trigger false positives.
- Implicit compiler-generated functions may cause spurious warnings.
- CUDA cooperative groups and other advanced APIs may not be fully understood.

### CG004 (Shared Memory)
- Static shared memory (`__shared__ int buf[256]`) is not flagged (correctly so).
- Kernel function pointers used for indirect launches are not tracked.
- Multiple `extern __shared__` declarations in one kernel are not specially handled.

### CG005 (Memcpy Direction)
- Only `cudaMalloc` and direct `malloc`/`new` provenance is tracked.
- `cudaMallocManaged`, `cudaMallocHost`, and other allocators are not recognized.
- Pointer arithmetic and casting break tracking.
- Global/static pointers are not tracked.

## Platform Limitations

- **Linux only.** The tool is designed for Linux development workflows.
- **Requires LLVM/Clang libraries** (version 14 or later recommended).
- **CUDA headers** are needed for full parsing accuracy but not for the analysis logic itself (can use `-nocudalib -nocudainc` for analysis without CUDA toolkit installed).

## What CudaGuard IS Good At

Despite these limitations, CudaGuard is effective at:
- Catching the most common CUDA error-handling omissions early.
- Flagging obvious launch configuration mistakes before runtime failure.
- Identifying host/device qualifier issues that would cause nvcc compilation errors.
- Providing actionable, compiler-style diagnostics with file, line, column, and fix hints.
- Integrating into build workflows via compilation database and wrapper mode.
